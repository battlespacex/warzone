## 1. Capture Shot

Investigated `initWarzoneCaptureShot`, `captureShot`, `composeCaptureBlob`, `copyNextSceneFrame`, `drawOperationalOverlayLayers`, `rasterizeDomLayer`, `drawBranding`, `loadImage` and `getCaptureErrorMessage` in `dev/assets/js/warzone-capture-shot.js`; toolbar markup in `dev/partials/header.html`/`nav.html`; imagery providers and Viewer creation in `warzone-globe.js`; and the DOM generated by hotspots/radar labels. No imagery, globe, GNSS, radar or satellite code was modified.

The existing capture scope is the Cesium canvas at drawing-buffer resolution, the map-linked `#warzone-hotspot-layer` and `#wz-radar-label-layer` DOM layers, and two branding images, exported as PNG. It does not capture the entire application chrome or floating widgets. No html2canvas or other general DOM capture library is involved. This scope and the file-picker/share/download path are retained.

The globe is copied synchronously during `scene.postRender`, before a non-preserved WebGL framebuffer becomes unavailable. Normal Viewer creation uses `preserveDrawingBuffer: false`; report-capture mode uses true. Changing that global setting is unnecessary for this existing synchronized read path and was avoided.

Confirmed code defects: every SecurityError was described as a visible imagery CORS failure, without identifying which compositing stage failed. DOM overlays were rasterized as Blob-backed SVG foreignObjects, a browser portability hazard. Overlay errors were logged and skipped, allowing incomplete captures to be reported as successful; branding image load failures were also silently skipped.

The fix serializes the same overlay snapshot into an SVG data URL, checks canvas readability after the map and each overlay/branding stage, and preserves the original error name/cause with a stage label. Failed required overlays/branding abort the capture rather than silently disappearing. No basemap substitution, security flag, no-cors fetch or proxy was added. Existing dimensions, overlay offsets and branding layout are unchanged. [Chromium's description of SVG/foreignObject URL taint differences](https://groups.google.com/a/chromium.org/g/blink-dev/c/JpA2vmA9XT8/m/ZbcAIeq7AQAJ) explains the portability choice; it does not prove that it was the exact cause in the user's browser.

**The exact live tainting source remains unconfirmed.** Neither the browser/version nor failing compositing stage was available. Computer Use reported an unavailable native pipe/browser host, and Playwright Chrome launch failed with `spawn EPERM`. Direct GET/header samples of Esri World Imagery and World Boundaries/Places, with `Origin: http://localhost:4173`, failed through the configured network proxy; no CORS response header was obtained. The source defaults to Esri but also supports configured Google/self-hosted imagery; no runtime provider selection was observed. Do not blame any particular provider from these results.

Canvas security is still enforced. If the new error identifies map imagery, inspect the active provider and actual tile/asset requests in DevTools. Cross-origin assets must be CORS-readable through provider-supported configuration; genuinely unreadable sources cannot be exported by this pipeline. If it identifies a DOM layer, inspect that layer's image/filter/font resources. SVG-as-image contexts restrict external resources; this change is not a full HTML renderer and full-fidelity label/font rendering still needs visual inspection. [MDN's SVG image restrictions](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image) and [canvas CORS rules](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image) describe those limits.

## 2. Report modal

Investigated `initOperationalReportsModal`, `openOperationalReportsModal`, `getOperationalReportBackgroundTargets`, `setOperationalReportBackgroundBlocked`, `handleOperationalReportKeydown`, `setReportsStatus`, `populateOperationalReportSelector`, `loadOperationalReportHistory`, `openOperationalReportViewer` and `downloadSelectedOperationalReport` in `essential.js`; modal markup/styles; shared modal queue/focus behavior in `warzone-boot.js`; report URL/history adapters in `supabase.js`; PDF.js viewer code; and `server/generated-report-preview.js`.

Confirmed structural cause: `dev/pages/index.html` included `partials("popups")` twice. Both gate layers and all Report controls had duplicate IDs. Handlers use getElementById, while both full-screen gate layers participate in the report-open stacking/pointer rules. This makes ID binding ambiguous and lets the later gate cover the earlier modal. The single extra include was removed; no persistent container replacement or Viewer initialization was introduced. The generated production HTML now has exactly one gate layer, one Report modal and one copy of its controls. Browser pointer behavior was not directly observed.

A second confirmed defect explains the blank body on unavailable reports: the status paragraph is inside the loader, but error/empty paths hide that loader before setting the status text. `setReportsStatus` now keeps the containing loader visible for messages and hides only its spinner. The existing typography/classes remain intact; no stylesheet was changed.

`loadOperationalReportHistory` now resets selection/download state and stale preview callbacks when the type changes, disables the date selector while loading, handles returned API errors and displays distinct 401/403/unavailable states. Empty results display a disabled “No reports available” option. History sequence checks prevent earlier responses replacing newer selections. The three existing types remain 72-hour operational report, daily briefing and weekly briefing. No report content was invented and no authentication control or endpoint was changed.

Preview/frame/PDF URLs, HTML-versus-PDF selection and the existing download generator remain unchanged. Download stays disabled until a report preview loads and metadata supplies a usable PDF URL without `pdf_available: false`. Actual remote artifact availability still depends on the existing API and storage delivery.

Read-only checks through the existing local generated-report router found three daily reports. One existing report's HTML and PDF preview/download URLs returned 200 with the expected MIME types. Downloaded PDF bytes had a valid `%PDF-` header and parsed successfully as 17 pages, 3,513,117 bytes. Local 72-hour/weekly catalogues returned empty lists; the local router currently lists daily artifacts only. This does not establish that the remote API has no 72-hour/weekly reports. No authenticated browser/API acceptance or PDF-generation job was run.
