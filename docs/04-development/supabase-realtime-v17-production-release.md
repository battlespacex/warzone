## Package and exact scope

- `supabase-realtime-v17-production-preflight.sql` is a single read-only current-schema query. It reads catalog metadata, not operational rows.
- `supabase-realtime-v17-production-migration.sql` installs the **exact** V1.4/V1.6-tested `stratops_skip_identical_ais_event_update()` trigger body and `zzzz_stratops_skip_identical_ais_event_update` on `public.events`. Its production guard has no staging marker requirement. It aborts on schema/index/publication/trigger drift. Its 5-second lock timeout avoids waiting indefinitely for a busy table.
- `supabase-realtime-v17-production-rollback.sql` removes only that trigger and function, with a guard that verifies the expected trigger/function pair. It does not rewrite data.
- The five-second ADS-B and AIS worker cadence, API, frontend access rules, `tracks`, both history tables, and all other event writes remain unchanged.

The migration's trigger/function definition from `CREATE FUNCTION` through `COMMIT` was compared exactly after newline normalization with the locally validated V1.4 staging definition and matched. The only new production behavior is suppressing a row UPDATE when an existing AIS `signal` event has `ais-` source/dedupe keys and **every** `NEW` column is identical to `OLD`. INSERT, DELETE, changed position, source observation time, metadata, classification, status, and all non-AIS updates retain their previous path. `tracks.updated_at` and history `last_seen_at` still advance on worker observations. This preserves the data used by live tracking, stale detection, AOI, CTR, intelligence alerts, and reporting; the authenticated deployed user flows remain a release smoke-test requirement, not a claimed local verification.

## Detecting excess usage after release

Supabase bills Realtime database changes **per receiving client** and also counts Broadcast and Presence messages. The organization Usage page is the authoritative billing-cycle total; by default it includes all projects. Use its project filter to attribute Warzone activity. The Realtime product report separates Postgres Changes, Broadcast, Presence, Connected Clients, and errors. A lower `events` row UPDATE rate is useful supporting evidence, but does not equal billable messages; unchanged `tracks` heartbeats and client fan-out remain. See [Supabase Realtime Messages usage](https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages) and [Realtime Reports](https://supabase.com/docs/guides/realtime/reports).

Record the same project and time window before/after: organization Realtime Messages total, Warzone project total, Postgres Changes rate, connected clients, Broadcast/Presence rates, `events` and `tracks` UPDATE deltas, worker/API error rate, and observed tracker freshness. Use the existing offline `apps/worker/scripts/realtime-usage-budget.mjs` with the actual billing-cycle total and dates to project against the **4-million-message goal**; it sends no network request. If usage stays high, first distinguish other projects, `tracks` updates, other event writers, Broadcast/Presence, and more connected clients before considering another change. Local savings do **not** establish the monthly goal or a dollar saving.
