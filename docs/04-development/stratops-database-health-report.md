## Implemented backend corrections

- Preserve strict 72-hour visibility and the existing normalization/MEE fixes, global ingestion, stored backlog replay, ID-based page collection, original timestamps and rejection diagnostics. The four conflict SQL files retain **exact URL plus matching source-ID metadata** for legacy ownership. Generic news/OSINT/Reddit/strike alone never grants deletion ownership.
- Separate visibility from deletion. Bounded physical deletion checks satellite observations, source links and both operational report tables. Held expired events stay physically stored but disappear from the active map. The previous seven-day blind event/raw deletes now call a dependency-aware RPC. Aircraft log and cluster retention rules are unchanged.
- Every destructive control starts **disabled**. A verified external backup reference and review timestamp must be explicitly recorded before a physical cleanup batch can run. No historical undated MEE deletion is provided. Feed cleanup retains the latest 300 dated Intel Wire reports (the API maximum), event-linked reports and report-referenced evidence, even when older than the map window.
- Conflict escalation alerts inherit the original parent's expiry, never a refreshed current time. New already-expired conflict alerts are cleared immediately. Existing owned-parent corrections and separately reviewed stale orphan escalation archival are bounded SQL functions; neither is automatically invoked. Historical archival is a status change, not deletion. Independent siren/network alert lifecycles are unchanged.
- Source registry uses a bounded 60-second cache, five-second negative cache, in-flight coalescing and invalidation after a successful registry sync. Read errors are not cached. Administrative registry edits can take up to 60 seconds to propagate; source authorizations are not user/subscription permissions.
- Identical raw evidence within the reuse window is reused only when substantive content, payload, URL, original publication and source identity match. Changed coordinates or other evidence still create a new raw snapshot. Existing `raw_items(hash)` is reused; no new hash index is required.
- Source-link writes and backfill use the same batch RPC. It locks each parent pair, verifies both parents, preserves the existing supporting-source default and avoids duplicate links. The missing-RPC compatibility fallback is intentionally reported as non-atomic; install the SQL before worker activation to obtain concurrency guarantees.
- Conflict storage compares substantive values before upserts. Unchanged reports avoid JSON rewrites; a separate batched freshness-only update occurs opportunistically after five minutes. Compaction removes only byte-identical copies of retained columns, preserving unique text, media, normalization, source attribution and deduplication evidence. Historical rows are not bulk-compacted or deleted.
- Country codes are filled from resolved incident geography using the existing local ISO crosswalk, including missing codes on later promotions. No guessed city coordinates or new geocoding API was introduced.
- Copernicus daily-row initialization no longer overwrites a concurrently initialized counter. A service-only atomic increment RPC replaces read/modify/write when installed. Fresh admission reads and existing provider quota CAS/reservations remain intact; no quota cache or relaxed limit was added.
- S3 cleanup retains pinned or uncertain report objects, retries failed deletions via expired rows that still have storage keys, and clears stale storage/image references only after successful deletion. Report generation in progress holds cleanup. Any satellite observation blocks physical parent deletion, including the four expired owned-event observations. Independent/unverified satellite events and orbital tracking are not reclassified or removed.
- Security migration captures baseline ACL/RLS state privately. It enables RLS on the reviewed unprotected tables, preserves guest/authenticated SELECT for events/tracks/active alerts, denies direct access to internal raw/worker/source tables, and removes client mutation/administrative grants from backend-managed operational tables. Existing SELECT grants/RLS on other operational tables are preserved. `stratops_subscriptions`, auth users, report job functions, provider quota functions and private authorization policies are not rewritten. Unexpected inherited rights or restrictive public-read policies abort the transaction instead of being silently replaced.

A non-isolated combined run encountered persisted test quota holds; rerunning with the repository's prescribed `provider-quota-isolation.js` harness passed. No production quota ledger was reset.

Identical raw evidence causes no duplicate insert; changed coordinates do. These are component results, **not claimed production row/WAL/latency reductions**.

Tests cover original UTC expiry at 24/48/71/72/73 hours, failed refresh preservation, deduplication, ownership, parser/geography behavior, country-code origin, source history defaults, counter initialization races, and pinned-preview retention. ## Exact manual execution sequence

Do not paste all SQL files into one request. Run transactional migrations as complete individual scripts; execute a proposed `CREATE INDEX CONCURRENTLY` statement alone outside a transaction. [PostgreSQL concurrent index guidance](https://www.postgresql.org/docs/17/sql-createindex.html) and [RLS documentation](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) explain these distinctions.

1. **External backup first.** Save a restorable database backup and the current definitions/grants. Export the proposed source-link cleanup population with IDs and attribution. Keep the original audit ZIP. Backup source/report/S3 metadata before approving deletion. Do not duplicate the entire 450 MB source table into another database table merely to reclaim storage.
2. Run `supabase-conflict-72h-preflight.sql`, `supabase-db-sources-preflight.sql`, `supabase-db-alerts-preflight.sql`, `supabase-db-security-preflight.sql`, and `supabase-db-performance-preflight.sql`. These are read-only. Reconfirm live ownership, NULL references, report pins, active generating reports, FKs/cascades, role inheritance/policies, callable routines and all index definitions. The source and alert preflights contain count/sample deletion/correction previews.
3. Compare the three user-created index definitions and their `indisvalid/indisready` values. Review EXPLAIN plans for the actual recent-track and active-alert queries. The performance preflight emits optional DDL only if no usable full leading `events(source_url)` index exists. Run only returned, reviewed concurrent DDL, separately. No unique/duplicate/timestamp index is automatically removed. Reuse existing source-parent, raw hash and publication-time indexes.
4. Run `supabase-db-health-foundation.sql`. It creates private controls and service-only dependency guards. Every cleanup control remains OFF. It does not delete records or add a paid service/cron dependency.
5. Run `supabase-db-sources-migration.sql`. Installs the atomic source-link RPC and disabled, bounded orphan cleanup. No FK or uniqueness constraint is added over unknown historical semantics.
6. Run `supabase-db-performance-migration.sql`. Installs atomic Copernicus increments only; it does not recreate the three indexes. Existing provider quota admission protections remain unchanged.
7. Run the revised `supabase-conflict-72h-migration.sql`. It preserves strict proven legacy ownership, timestamp triggers, worker fallback and optional existing pg_cron scheduling. Physical cleanup is still OFF. Unlike the earlier revision, no blocking index creation or unguarded cascading event delete occurs here.
8. Run `supabase-db-alerts-migration.sql`. After reviewing/exporting the proven-parent preview, manually call `SELECT public.stratops_correct_conflict_alerts(500);` repeatedly as needed, verifying results between batches. Originals of changed lifecycle fields are backed up privately. This does not guess ownership of orphaned alerts.
9. Run `supabase-db-security-migration.sql` in a controlled rollout window **after reviewing restrictive policies and inherited roles**. It snapshots client/service ACLs and original RLS. Any unexpected inherited write/internal-read permission aborts. Verify public SELECT through both roles before continuing. Do not change subscription/user policies to force a pass.
10. Run all five verification scripts: `supabase-conflict-72h-verification.sql`, `supabase-db-sources-verification.sql`, `supabase-db-alerts-verification.sql`, `supabase-db-security-verification.sql`, `supabase-db-performance-verification.sql`. Manually activate the updated worker only after SQL dependencies are installed; no deployment is performed by this task. Verify guest/authenticated entry, existing Realtime/tracker flows, source replay, alert expiry and report previews. Check the worker logs for missing-RPC fallbacks rather than treating them as atomic success.
11. **Enable only the reviewed physical cleanup.** In SQL Editor, replace the placeholder with your actual verified backup identifier, then run:

    ```sql
    UPDATE stratops_maintenance.controls
    SET enabled=true, backup_reference='ACTUAL VERIFIED BACKUP IDENTIFIER', reviewed_at=now()
    WHERE name IN ('conflict','working_history');
    ```

    The worker then performs bounded maintenance; no periodic dataset reset occurs. Review held counts. Source/report/satellite-held records remain stored beyond 72 hours but are not active map incidents. Report generation also holds cleanup. Run `SELECT public.maintain_conflict_intelligence_72h();` manually only when you intend a real cleanup batch after this approval.
12. **Orphan source cleanup is separate.** After confirming non-NULL dangling references, report holds, export completeness and plans, enable only `source_orphans` using the same reviewed control fields. Call `SELECT public.stratops_prune_source_orphans(1000);` for one bounded batch, verify counts/attribution, then repeat deliberately. NULL-ID history and singly missing parents are excluded. Do not use the CSV's 1,506,499 count as a DELETE LIMIT or assumed final total. Deletions are irreversible without the external export.
13. **Historical escalation archival is separate.** Review the orphan escalation preview. If approved, enable `historical_escalations` with its backup reference/review timestamp, then call `SELECT public.stratops_archive_stale_escalations(500);` in reviewed batches. Only stale 30-day orphan escalation status is changed; unrelated siren/network categories and original event timestamps remain untouched. No expiry date is fabricated for unproven parents.
14. Capture equivalent workload measurements using the performance verification queries over a comparable interval. Compare row counters, WAL, query plans and latency; do not reset cumulative statistics. Review autovacuum after cleanup. Ordinary `VACUUM (ANALYZE)` can make freed space reusable but DELETE does not promise a smaller disk file. No VACUUM FULL, blocking REINDEX, extension installation or index drop is executed or prescribed automatically. Pro/Micro apparent capacity does not justify a paid infrastructure change.

### Rollback order and irreversible effects

Disable all controls first: `UPDATE stratops_maintenance.controls SET enabled=false;`. Roll back security through `supabase-db-security-rollback.sql` if necessary (it restores the captured potentially unsafe baseline, so use deliberately). Roll back alert lifecycle using `supabase-db-alerts-rollback.sql`; later operationally changed alerts require individual review. Then use `supabase-db-sources-rollback.sql`, `supabase-db-performance-rollback.sql`, `supabase-conflict-72h-rollback.sql`, and finally `supabase-db-health-foundation-rollback.sql` after callers are removed. Private snapshots remain for audit. No schema CASCADE or existing-index removal occurs. Reinstating old code is a separate reviewed decision; old blind pruning must not be restarted against protected dependencies. Deleted source/feed/event rows require external backup restoration; S3 objects deleted after proving no report references also require storage backup to restore. No rollback can invent them.
